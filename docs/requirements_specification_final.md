# Requirements Specification

**Project:** Sillycation  
**Version:** 1.0  
**Status:** Final  
**Date:** 2026-09-15

## 1. Actors

The system defines three roles:

- **Registered User**: a user who owns an account and can create trips or request to join existing ones.
- **Trip Creator**: the registered user who created a specific trip. The creator is automatically a participant of that trip.
- **Participant**: a registered user whose participation in a trip has been approved.

Roles are **trip-specific**. A user may be the creator of one trip and a participant in another.

A user may participate in multiple trips provided that the date intervals of the trips do not overlap while those trips are `PLANNED` or `ACTIVE`.

## 2. Functional Requirements

### FR-01 — User Registration

**Requirement**

The system shall allow a new user to create an account by providing:

- username;
- email;
- password.

The username and email address shall be unique.

**User Story**

> As a new user, I want to create an account so that I can participate in trips and use Sillycation.

**Definition of Done**

FR-01 is done when:

- a user can register through the API;
- duplicate usernames are rejected;
- duplicate email addresses are rejected;
- mandatory fields are validated;
- passwords are not stored in plain text;
- successful registration creates a persistent user;
- automated tests cover successful and unsuccessful registration.

---

### FR-02 — User Authentication

**Requirement**

The system shall allow registered users to authenticate using their credentials.

Authenticated users shall receive an authentication mechanism, such as a JWT token, for accessing protected operations.

**User Story**

> As a registered user, I want to log in so that I can access my trips and perform authenticated operations.

**Definition of Done**

FR-02 is done when:

- valid credentials successfully authenticate the user;
- invalid credentials are rejected;
- protected API endpoints cannot be accessed without authentication;
- an authenticated user can access resources for which they are authorized;
- automated tests cover successful login, invalid credentials, and unauthenticated access.

---

### FR-03 — Trip Creation

**Requirement**

Any authenticated user shall be allowed to create a trip.

A trip shall contain:

- name;
- creator;
- optional description;
- start date;
- end date;
- lifecycle status.

The creator automatically becomes a participant of the trip.

A newly created trip shall have status `PLANNED`.

The start date shall not be later than the end date.

A user shall not be allowed to create a trip whose date interval overlaps with another `PLANNED` or `ACTIVE` trip in which that user already participates.

**User Story**

> As a registered user, I want to create a trip so that my group can collect and rank memorable episodes during the holiday.

**Definition of Done**

FR-03 is done when:

- an authenticated user can create a trip;
- the creator is automatically associated with the trip as a participant;
- the initial state is `PLANNED`;
- start date and end date are mandatory;
- a trip with `start_date > end_date` is rejected;
- creation is rejected if the new trip overlaps with another `PLANNED` or `ACTIVE` trip in which the creator participates;
- unauthenticated users cannot create trips;
- the trip is persisted;
- automated tests verify successful creation, date validation, overlap validation, and authorization.

---

### FR-04 — Trip Invitation Code

**Requirement**

Each trip shall have a unique invitation code generated by the system.

Authenticated users may use this code to request access to the trip while the trip is `PLANNED`.

**User Story**

> As a trip creator, I want to share an invitation code so that my friends can easily find and request to join my trip.

**Definition of Done**

FR-04 is done when:

- a unique invitation code is generated for every trip;
- the creator can retrieve the invitation code;
- an authenticated user can submit the code;
- invalid or unknown codes are rejected;
- invitation codes cannot be used to request access once the trip is no longer `PLANNED`;
- automated tests cover valid, invalid, and unavailable invitation codes.

---

### FR-05 — Join Trip Request

**Requirement**

An authenticated user may request to join a `PLANNED` trip using its invitation code.

Submitting the code creates a pending join request. The user does not become a participant until the request is approved by the trip creator.

A user who is already a participant of the same trip cannot submit another join request.

A user may participate in multiple trips only if their date intervals do not overlap. A join request shall therefore be rejected if the target trip overlaps with another `PLANNED` or `ACTIVE` trip in which the user is already a participant.

For two trips, the date intervals overlap when:

```text
new_trip.start_date <= existing_trip.end_date
AND
new_trip.end_date >= existing_trip.start_date
```

**User Story**

> As a registered user, I want to request access to my friends' trip so that I can participate in Sillycation with them.

**Definition of Done**

FR-05 is done when:

- a valid invitation code for a `PLANNED` trip creates a pending join request;
- duplicate pending requests are prevented;
- existing participants cannot request to join the same trip again;
- requests to trips that are not `PLANNED` are rejected;
- requests are rejected when the target trip overlaps with another `PLANNED` or `ACTIVE` trip in which the user participates;
- requests for non-overlapping trips are allowed;
- the pending request is persisted;
- automated tests cover the joining workflow, including overlapping and non-overlapping trips.

---

### FR-06 — Participant Approval

**Requirement**

Only the trip creator shall be allowed to approve or reject pending join requests while the trip is `PLANNED`.

When approving a request, the system shall re-check that the user does not already participate in another overlapping `PLANNED` or `ACTIVE` trip.

An approved user becomes a participant of the trip.

A rejected user does not become a participant.

**User Story**

> As a trip creator, I want to approve who joins my trip so that only members of my travelling group can access it.

**Definition of Done**

FR-06 is done when:

- the creator can list pending requests;
- the creator can approve a request while the trip is `PLANNED`;
- the creator can reject a request while the trip is `PLANNED`;
- approval is rejected if the applicant has acquired a conflicting overlapping trip since creating the request;
- approved users become participants;
- rejected users do not become participants;
- ordinary participants cannot approve or reject requests;
- requests cannot be approved or rejected after the trip becomes `ACTIVE`;
- automated tests verify authorization, overlap validation, and state changes.

---

### FR-07 — View Trip Participants

**Requirement**

Every participant shall be allowed to see the list of participants belonging to a trip in which they participate.

**User Story**

> As a participant, I want to see who is part of the trip so that I know who is participating in the game.

**Definition of Done**

FR-07 is done when:

- participants can retrieve the participant list;
- users outside the trip cannot access it;
- the creator is included in the participant list;
- the returned information corresponds to persisted membership data;
- authorization is covered by automated tests.

---

### FR-08 — Trip Lifecycle Management

**Requirement**

A trip shall follow this lifecycle:

```text
PLANNED -> ACTIVE -> COMPLETED -> ARCHIVED
```

Backward transitions shall not be permitted.

Only the trip creator may explicitly change the trip lifecycle.

#### `PLANNED`

- users may request to join the trip;
- the creator may approve or reject pending join requests;
- trip membership may change;
- episodes cannot be created, submitted, or voted on.

#### `ACTIVE`

- the participant set is locked;
- no new join requests or approvals are allowed;
- participants may create and submit episodes;
- eligible participants may vote.

A trip may transition from `PLANNED` to `ACTIVE` only when:

- the trip start date has been reached;
- the trip has at least two participants.

#### `COMPLETED`

- the game is finished;
- no participants, episodes, or votes may be added or modified;
- the final ranking is definitive;
- the trip remains visible in the normal completed-trip history.

#### `ARCHIVED`

- the trip remains available for historical access;
- the trip is read-only;
- the trip is no longer shown in the default list of active or completed trips and is accessible from the archive/history view.

**User Story**

> As a trip creator, I want to control the lifecycle of the trip so that Sillycation follows the different phases of the holiday.

**Definition of Done**

FR-08 is done when:

- all four statuses exist;
- only `PLANNED -> ACTIVE -> COMPLETED -> ARCHIVED` transitions are accepted;
- backward transitions and skipped transitions are rejected;
- only the creator can execute lifecycle transitions;
- transition to `ACTIVE` is rejected before the start date;
- transition to `ACTIVE` is rejected if fewer than two participants exist;
- becoming `ACTIVE` locks the participant set;
- `COMPLETED` and `ARCHIVED` trips reject game-data modifications;
- archived trips are excluded from the default trip list and remain available in the archive/history view;
- automated tests cover valid and invalid lifecycle transitions.

## 3. Episode Management

### FR-09 — Create Episode

**Requirement**

A participant of an `ACTIVE` trip shall be allowed to create an episode.

An episode shall contain:

- title;
- description;
- date;
- protagonist;
- lifecycle status;
- author.

The author of an episode does not necessarily have to be its protagonist.

A newly created episode shall have status `DRAFT`.

The protagonist shall be a participant of the same trip.

The episode date shall fall within the trip date interval.

**User Story**

> As a trip participant, I want to record a funny episode so that the group can remember and rate what happened.

**Definition of Done**

FR-09 is done when:

- participants of an `ACTIVE` trip can create episodes;
- the author is stored;
- the protagonist belongs to the same trip;
- the initial state is `DRAFT`;
- mandatory fields are validated;
- an episode date outside the trip date interval is rejected;
- users outside the trip cannot create episodes;
- episodes cannot be created for `PLANNED`, `COMPLETED`, or `ARCHIVED` trips;
- automated tests verify domain and authorization rules.

---

### FR-10 — Edit or Delete Draft Episode

**Requirement**

The author of an episode may edit or delete it while its status is `DRAFT`.

Once the episode is submitted, it cannot be edited or deleted.

**User Story**

> As the author of an episode, I want to correct it before submitting it so that incorrect information is not shown to the group.

**Definition of Done**

FR-10 is done when:

- the author can edit a `DRAFT` episode;
- the author can delete a `DRAFT` episode;
- another participant cannot edit or delete it;
- `SUBMITTED`, `VOTING`, and `COMPLETED` episodes cannot be edited or deleted;
- updates continue to satisfy all episode validation rules;
- invalid operations return an appropriate error;
- automated tests verify all cases.

---

### FR-11 — Submit Episode

**Requirement**

The author of a `DRAFT` episode shall be able to submit it while the trip is `ACTIVE`.

Submitting an episode shall perform the transition:

```text
DRAFT -> SUBMITTED
```

A submitted episode becomes visible to all trip participants and becomes immutable.

The system shall then open voting according to FR-12.

**User Story**

> As an episode author, I want to submit my episode so that the other participants can see and vote on it.

**Definition of Done**

FR-11 is done when:

- the author can submit a valid `DRAFT` episode;
- another participant cannot submit the author's draft;
- the state changes from `DRAFT` to `SUBMITTED`;
- the episode becomes visible to trip participants;
- the submitted episode becomes immutable;
- submission is rejected when the trip is not `ACTIVE`;
- submission is rejected from any state other than `DRAFT`;
- automated tests verify authorization and valid and invalid transitions.

---

## 4. Voting

### FR-12 — Open Episode Voting

**Requirement**

A submitted episode shall enter the voting phase through the transition:

```text
SUBMITTED -> VOTING
```

Opening voting is part of the submission workflow and shall occur automatically after successful submission.

Voting is available only while the trip is `ACTIVE`.

**User Story**

> As a participant, I want submitted episodes to enter the voting phase so that the group can rate them.

**Definition of Done**

FR-12 is done when:

- a successfully submitted episode automatically enters `VOTING`;
- voting is available only during an `ACTIVE` trip;
- only eligible participants can vote;
- voting cannot occur on `DRAFT`, `SUBMITTED`, or `COMPLETED` episodes;
- automated tests verify valid and invalid states.

---

### FR-13 — Vote on Episode

**Requirement**

Each eligible participant shall be able to assign an integer rating from **1 to 5** to an episode in `VOTING`.

Each eligible user may cast at most one vote per episode.

Votes cannot be modified or deleted after submission.

The backend shall validate the vote value independently of any frontend input control.

**User Story**

> As a trip participant, I want to rate an episode from 1 to 5 so that my opinion contributes to the final ranking.

**Definition of Done**

FR-13 is done when:

- only eligible trip participants can vote;
- integer values from 1 to 5 are accepted;
- values outside the range 1 to 5 are rejected by the backend;
- non-integer vote values are rejected;
- a user cannot cast more than one vote for the same episode;
- votes cannot subsequently be edited or deleted;
- votes are persisted;
- automated tests verify all constraints, including direct API requests with invalid values.

---

### FR-14 — Protagonist Voting Restriction

**Requirement**

The protagonist of an episode shall not be allowed to vote on that episode.

The episode author may vote if the author is not also the protagonist.

**User Story**

> As a participant, I want protagonists to be excluded from rating their own episodes so that scores are determined by the rest of the group.

**Definition of Done**

FR-14 is done when:

- the protagonist is identified correctly;
- voting attempts by the protagonist are rejected;
- an author who is not the protagonist may vote;
- every other eligible participant may vote;
- automated tests verify protagonist, author, and ordinary participant cases.

---

### FR-15 — Automatic Episode Completion

**Requirement**

An episode shall automatically become `COMPLETED` when every eligible participant has voted.

Eligible voters are all participants whose membership was locked when the trip became `ACTIVE`, except the episode protagonist.

Therefore:

```text
expected_votes = number_of_trip_participants - 1
```

An episode cannot be manually closed while eligible votes are missing.

**User Story**

> As a participant, I want an episode to close automatically once everyone eligible has voted so that no one has to manage the voting manually.

**Definition of Done**

FR-15 is done when:

- the system determines the eligible voter set from the locked participant set;
- the protagonist is excluded;
- the episode remains `VOTING` while at least one eligible vote is missing;
- after the final eligible vote, the episode automatically becomes `COMPLETED`;
- no additional votes are accepted after completion;
- the final episode score is calculated according to FR-16;
- automated tests include groups of different sizes.

---

## 5. Ranking

### FR-16 — Episode Score Calculation

**Requirement**

For every `COMPLETED` episode, the system shall calculate its score as the arithmetic mean of all valid votes.

Example:

```text
votes = [5, 4, 3]
episode_score = 4.0
```

**User Story**

> As a participant, I want to see the final score of an episode so that I know how the group rated it.

**Definition of Done**

FR-16 is done when:

- only persisted valid votes are included;
- the arithmetic mean is calculated correctly;
- the score is exposed through the API;
- an episode does not expose a definitive score before it becomes `COMPLETED`;
- automated tests verify the calculation.

---

### FR-17 — Participant Ranking

**Requirement**

The system shall maintain a ranking of trip participants based on the scores of `COMPLETED` episodes in which they are protagonists.

The participant score shall be:

```text
participant_score =
    sum(score of each COMPLETED episode
        where participant is protagonist)
```

Only `COMPLETED` episodes contribute to the ranking.

Participants with higher total scores appear higher in the ranking.

**User Story**

> As a participant, I want to see the ranking of all travellers so that we can determine who accumulated the funniest or most highly rated episodes.

**Definition of Done**

FR-17 is done when:

- every trip participant appears in the ranking;
- only `COMPLETED` episodes contribute;
- episode scores are attributed to their protagonist;
- scores are summed correctly;
- participants are ordered by descending total score;
- participants with no completed episodes have score `0`;
- automated tests verify ranking calculation.

---

### FR-18 — Ranking Tie Handling

**Requirement**

Participants with the same total score shall share the same ranking position.

Competition ranking shall be used, meaning that the position following a tie skips the corresponding number of positions.

Example:

| Participant | Score | Position |
|---|---:|---:|
| Anna | 20 | 1 |
| Luca | 17 | 2 |
| Marco | 17 | 2 |
| Sara | 10 | 4 |

**User Story**

> As a participant, I want equal scores to produce equal positions so that the final ranking is fair.

**Definition of Done**

FR-18 is done when:

- identical total scores produce the same position;
- the position following a tie follows competition-ranking rules;
- ranking behaviour is deterministic;
- automated tests include at least one tied ranking.

---

## 6. Trip Completion

### FR-19 — Complete Trip

**Requirement**

Only the trip creator may complete an `ACTIVE` trip.

A trip may transition to `COMPLETED` only when:

1. the trip end date has been reached or passed;
2. there are no episodes in `DRAFT`;
3. there are no episodes in `SUBMITTED`;
4. there are no episodes in `VOTING`;
5. every existing episode is therefore `COMPLETED`.

Once the trip becomes `COMPLETED`:

- no participants may be added or removed;
- no episodes may be created, edited, or deleted;
- no votes may be cast, edited, or deleted;
- existing game data becomes read-only;
- the participant ranking becomes final.

**User Story**

> As a trip creator, I want to complete the trip after its end date and once all episodes have been resolved so that the final ranking becomes official.

**Definition of Done**

FR-19 is done when:

- only the creator can request completion;
- completion is rejected before the trip end date;
- completion is rejected if any unresolved episode exists;
- completion succeeds when the date and episode conditions are satisfied;
- the state becomes `COMPLETED`;
- game-data write operations are rejected afterward;
- the final ranking remains accessible;
- automated tests cover successful completion and each rejection condition.

---

### FR-20 — Archive Trip

**Requirement**

The creator of a `COMPLETED` trip shall be allowed to archive it.

Archiving performs the transition:

```text
COMPLETED -> ARCHIVED
```

An archived trip shall remain visible to its participants in a dedicated archive/history view but shall not appear in the default list of active or completed trips.

An archived trip is read-only.

**User Story**

> As a trip creator, I want to archive an old trip so that it remains available as a memory without appearing in my regular trip list.

**Definition of Done**

FR-20 is done when:

- only `COMPLETED` trips can be archived;
- only the creator can archive a trip;
- the state changes to `ARCHIVED`;
- archived trips disappear from the default trip list;
- archived trips remain accessible to their participants through the archive/history view;
- no game-data state-changing operation is accepted;
- automated tests verify authorization, lifecycle restrictions, and visibility behaviour.

---

## 7. Dashboard

### FR-21 — Trip Dashboard

**Requirement**

The system shall expose a dashboard for every trip containing at least:

- trip information;
- trip status;
- participant list;
- episode list;
- episode statuses;
- completed episode scores;
- current participant ranking.

For `COMPLETED` trips, the dashboard shall display the final ranking.

For `ARCHIVED` trips, the same information shall remain available through the archive/history view.

**User Story**

> As a participant, I want a single overview of the trip so that I can quickly understand what happened, which episodes still need votes, and the current ranking.

**Definition of Done**

FR-21 is done when:

- participants can access the dashboard for trips in which they participate;
- non-participants cannot access it;
- all required information is available;
- displayed information corresponds to persisted data;
- rankings and episode statuses update after relevant actions;
- completed trips display the final ranking;
- archived trips remain readable from the archive/history view;
- API and frontend behaviour are tested.

## 8. Optional / Stretch Functional Requirements

### FR-22 — Episode Comments

**Requirement**

Participants shall be able to add comments to episodes belonging to their trip.

Comments may be created only while the trip is `ACTIVE`.

Comments become read-only when the trip is `COMPLETED` or `ARCHIVED`.

**User Story**

> As a participant, I want to comment on an episode so that we can discuss what happened.

**Definition of Done**

FR-22 is done when:

- a participant can add a comment to an episode of their own `ACTIVE` trip;
- users outside the trip cannot create or read comments;
- comments are persisted;
- comments are associated with their author and episode;
- new comments are rejected when the trip is `COMPLETED` or `ARCHIVED`;
- automated tests verify authorization and lifecycle restrictions.

---

### FR-23 — Episode Picture

**Requirement**

An episode may contain one optional picture reference.

The presence of a picture is not required to create or submit an episode.

**User Story**

> As an episode author, I want to attach a picture so that the episode is easier to remember.

**Definition of Done**

FR-23 is done when:

- an episode can be created without a picture;
- one supported picture reference can be associated with an episode;
- unsupported file types or invalid picture references are rejected;
- picture metadata is associated with the correct episode;
- the picture follows the same visibility rules as the episode;
- automated tests cover episodes with and without pictures.

---

### FR-24 — Final Loser Picture and Penalty

**Requirement**

When all conditions for trip completion are satisfied, the participant or participants in first place in the final ranking shall be identified as the trip **loser(s)**, because they accumulated the highest total score.

As part of the trip-completion operation, the trip creator may attach:

- one optional final picture;
- an optional textual description of the penalty.

The final picture and penalty are displayed on the completed-trip dashboard together with the final ranking.

If multiple participants share first place, they are considered co-losers.

Once the trip becomes `COMPLETED`, the final picture and penalty information are read-only.

**User Story**

> As a trip creator, I want to record the loser and the final penalty so that the trip ends with a memorable final result.

**Definition of Done**

FR-24 is done when:

- the system identifies the highest-ranked participant or all highest-ranked participants in case of a tie;
- the creator may attach a final picture and penalty description as part of trip completion;
- the final picture and penalty are associated with the trip;
- completing the trip does not require a picture or penalty;
- the information is displayed on the `COMPLETED` trip dashboard;
- the information cannot be modified after completion;
- archived trips preserve and display the same final information;
- automated tests cover a unique loser, tied co-losers, and completion without a final picture.

**Requirement**

The backend shall expose a documented and versioned REST API.

```text
/api/v1/trips
```

**User Story**

> As a frontend developer, I want a stable and documented REST API so that the client application can interact with the backend predictably.

**Definition of Done**

NFR-01 is done when:

- endpoints follow REST conventions;

- OpenAPI documentation is generated;

- API documentation is accessible during development.

### NFR-02 — Persistent Storage

**Requirement**

Application data shall persist across application restarts using a relational database accessed through repository abstractions.

The persistence implementation shall use SQLAlchemy. SQLite may be used as the default development and project database in order to keep deployment lightweight.

**User Story**

> As a user, I want my trips, episodes, votes, and rankings to remain saved so that no game data is lost when the application restarts.

NFR-02 is done when:

- restarting the application does not remove persisted data;

- domain logic does not depend directly on the database engine;
- the configured relational database can be initialized from a clean environment;
- integration tests verify persistence.

Protected operations shall require authentication, and each operation shall enforce domain-specific authorization.

**User Story**

## 10. Definitive Domain Rules

### 10.1 Trip Membership

1. Any authenticated user can create a trip.
2. The creator automatically becomes a participant.
3. Other users request to join through the trip invitation code.
4. A join request remains pending until accepted or rejected.
5. Only the trip creator may accept or reject requests.
6. Join requests and approvals are allowed only while the trip is `PLANNED`.
7. A user cannot join the same trip more than once.
8. A user may participate in multiple trips only if their date intervals do not overlap.
9. Overlap restrictions apply to `PLANNED` and `ACTIVE` trips.
10. The participant set becomes immutable when the trip becomes `ACTIVE`.

### 10.2 Trip Lifecycle

```text
PLANNED
   |
   v
ACTIVE
   |
   v
COMPLETED
   |
   v
ARCHIVED
```

No backward or skipped transitions are permitted.

#### `PLANNED`

- join requests may be created;
- the creator may approve or reject requests;
- membership may change;
- episodes cannot be created, submitted, or voted on.

#### `ACTIVE`

- membership is locked;
- episodes may be created and submitted;
- eligible participants may vote;
- the trip cannot return to `PLANNED`.

#### `COMPLETED`

- the trip end date has been reached or passed;
- all existing episodes are `COMPLETED`;
- game data is read-only;
- the ranking is final;
- the trip remains in the completed-trip history.

#### `ARCHIVED`

- the trip remains read-only;
- the trip is moved from the default trip list to the archive/history view.

## 11. Episode Rules

The episode lifecycle is:

```text
DRAFT
  |
  v
SUBMITTED
  |
  v
VOTING
  |
  v
COMPLETED
```

`SUBMITTED -> VOTING` occurs automatically as part of the submission workflow.

Rules:

1. Only participants may create episodes.
2. Episodes may be created only while the trip is `ACTIVE`.
3. The protagonist must belong to the same trip.
4. The author and protagonist may be different participants.
5. Only the author may edit or delete a `DRAFT`.
6. A submitted episode becomes immutable.
7. Submitted episodes are visible to all trip participants.
8. Only eligible participants may vote.
9. The protagonist cannot vote on their own episode.
10. Each eligible participant may vote at most once.
11. Vote values are integers from 1 to 5.
12. A submitted vote cannot be edited or deleted.
13. When every eligible participant has voted, the episode automatically becomes `COMPLETED`.
14. Only `COMPLETED` episodes contribute to the participant ranking.

---

## 12. Voting Eligibility and Episode Completion

For an episode with participant set:

```text
{A, B, C, D}
```

and protagonist:

```text
B
```

the eligible voters are:

```text
{A, C, D}
```

Therefore:

```text
expected_votes = trip_participant_count - 1
```

Formally:

```text
eligible_voters =
    trip.participants - {episode.protagonist}

episode_completed <=>
    every eligible voter has submitted exactly one vote
```

Because the participant set is frozen when a trip becomes `ACTIVE`, the eligible-voter set cannot change while an episode is being voted on.

---

## 13. Trip Completion Rule

A trip may become `COMPLETED` only if:

```text
trip.status == ACTIVE
AND
current_date >= trip.end_date
AND
there are no DRAFT episodes
AND
there are no SUBMITTED episodes
AND
there are no VOTING episodes
```

Equivalent condition:

```text
current_date >= trip.end_date
AND
all existing episodes are COMPLETED
```

Only the trip creator may execute:

```text
ACTIVE -> COMPLETED
```

---

## 14. Ranking Rule

For each participant:

```text
participant_score =
    sum(score of every COMPLETED episode
        where participant is protagonist)
```

For each completed episode:

```text
episode_score =
    sum(votes) / number_of_votes
```

Example:

| Participant | Episode | Score |
|---|---|---:|
| Anna | Lost her passport | 4.5 |
| Anna | Fell into the pool | 4.0 |
| Luca | Missed the bus | 3.5 |
| Marco | Wrong hotel room | 5.0 |

Final ranking:

| Rank | Participant | Total |
|---:|---|---:|
| 1 | Anna | 8.5 |
| 2 | Marco | 5.0 |
| 3 | Luca | 3.5 |

The participant with the highest total score is considered the trip loser for the purpose of FR-24.

If multiple participants share the highest total score, they are co-losers.

## 16. Core Domain Invariants

```text
INV-01
A Trip always has exactly one creator.

INV-02
The Trip creator is always also a Trip participant.

INV-03
A Trip start date cannot be later than its end date.

INV-04
A User cannot participate in two PLANNED or ACTIVE Trips whose date intervals overlap.

INV-05
Trip membership cannot change after the Trip becomes ACTIVE.

INV-06
A Trip can become ACTIVE only on or after its start date and with at least two participants.

INV-07
A protagonist must belong to the same Trip as the Episode.

INV-08
An Episode can be created only while its Trip is ACTIVE.

INV-09
An Episode can receive votes only while its state is VOTING.

INV-10
A protagonist cannot vote on their own Episode.

INV-11
A Participant can vote at most once on the same Episode.

INV-12
A Vote must be an integer in [1, 5].

INV-13
A submitted Vote cannot be modified or deleted.

INV-14
A SUBMITTED, VOTING, or COMPLETED Episode cannot be edited or deleted.

INV-15
An Episode becomes COMPLETED when every eligible voter has voted.

INV-16
Only COMPLETED Episodes contribute to the Participant ranking.

INV-17
A Trip cannot become COMPLETED before its end date.

INV-18
A Trip cannot become COMPLETED while unresolved Episodes exist.

INV-19
A COMPLETED Trip cannot receive new Participants, Episodes, or Votes.

INV-20
An ARCHIVED Trip is read-only.

INV-21
Trip lifecycle transitions cannot move backwards or skip states.

INV-22
Participants with the same ranking score share the same position.

INV-23
The participant or participants with the highest final score are the Trip loser(s).
```
